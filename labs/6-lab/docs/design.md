# DNS Resolver: итеративный алгоритм и обработка TC

## Общая схема

Программа `dns_resolver.cpp` принимает доменное имя, тип записи и необязательный флаг `-d`. Имена нормализуются к нижнему регистру; DNS-имена в пакетах кодируются метками с длиной, ответы разбираются с поддержкой DNS name compression.

1. Резолвер формирует стандартный DNS-запрос: `QR=0`, `RD=0`, `QDCOUNT=1`, класс `IN`, новый идентификатор запроса. Для DNSSEC-записей в дополнительных данных добавляется EDNS0 OPT с DO=1.
2. Первый запрос отправляется одному из известных IP-адресов корневых DNS-серверов (порт 53, UDP). Если сервер не отвечает, выбирается следующий.
3. Ответ сверяется с идентификатором транзакции, вопросом и форматом DNS. Из него извлекаются секции Answer, Authority и Additional.
4. Если в Answer есть искомая запись, она возвращается. Если указан CNAME, резолвер следует по цепочке; для имени в другой зоне может начать новый поиск от корневых серверов.
5. Если получено делегирование, из Authority извлекаются NS. Их адреса берутся из соответствующих A/AAAA в Additional (glue). Если glue нет, имена NS разрешаются отдельными итеративными запросами.
6. Поиск продолжается на следующем уровне до получения результата. Авторитетный NXDOMAIN или отсутствие записи, ошибки протокола, таймауты, недоступные серверы и зацикливания обрабатываются отдельно.

Установлены ограничения на количество переходов, число DNS-записей, размер пакета, глубину CNAME/NS и время ожидания каждого сервера. Файловый кэш сохраняет только положительные финальные результаты. Срок жизни кэшированной записи равен минимальному TTL среди возвращённых записей и пройденных CNAME.

## Как обрабатывается TC-флаг

Поле TC (`Truncated`) — бит `0x0200` во втором 16-битном слове DNS-заголовка. Оно означает, что UDP-ответ неполон. При обнаружении TC нельзя трактовать его содержимое как полный набор ресурсных записей: даже корректная заголовочная часть не гарантирует полноты остальных секций.

Алгоритм реализован в `DnsResolver::Exchange` и отдельных транспортных функциях `QueryUdp` и `QueryTcp`.

1. Программа отправляет DNS-запрос по UDP (RD=0) и получает датаграмму в буфер до 65535 байт. Проверяет длину заголовка, QR и идентификатор транзакции.
2. Если `TC=0`, DNS-ответ целиком разбирается функцией `ParseResponse`.
3. Если `TC=1`, программа **не разбирает обрезанные ресурсные записи**, а открывает новое TCP-соединение с **тем же IP-адресом DNS-сервера** на порт 53.
4. Сначала отправляет два байта длины исходного DNS-запроса в сетевом порядке, затем сам запрос. Идентификатор транзакции, домен, тип и RD остаются прежними.
5. С TCP-соединения в цикле читаются **ровно два байта длины** ответа, затем **ровно указанное количество байтов** DNS-сообщения. Это необходимо, поскольку TCP не сохраняет границы сообщений и один `recv()` не обязан вернуть всё.
6. Полный TCP-ответ проверяется через `ParseResponse`: ID, QR, вопрос, код ошибки, границы полей и ресурсных записей. Если TCP-ответ также содержит TC, пакет считается некорректным.
7. При ошибке соединения, неполном чтении или таймауте запрос может быть повторён; после исчерпания попыток резолвер пробует другой DNS-сервер текущего уровня. В `-d` печатается причина и факт смены протокола.

### Обработка ресурсов и таймаутов

- Сокет обёрнут в класс `FileDescriptor`. Деструктор вызывает `close()` при любом выходе, в том числе по исключению.
- TCP `connect()` запускается в неблокирующем режиме; готовность ожидается через `poll()` с ограничением времени. После соединения восстанавливается блокирующий режим.
- На отправку и приём установлены `SO_SNDTIMEO` и `SO_RCVTIMEO`. Циклы `send()`/`recv()` учитывают частичную передачу и `EINTR`.
- UDP-сокет использует `connect()` для фильтрации ответов от посторонних адресов; дополнительно проверяются DNS transaction ID и исходный вопрос.
- Транспортная ошибка не превращается в ложный ответ «нет записи». `NXDOMAIN`, `NOERROR` без подходящей записи и сетевые ошибки рассматриваются отдельно.

## Демонстрация

Для отчёта достаточно показать обычный запрос A/AAAA с `--no-cache`, подробный `-d`-лог переходов root → TLD → NS и запрос, в котором авторитетный сервер действительно вернул `TC=1`. В последнем логе появятся строки `TC=1 ... повторяем тот же запрос по TCP` и `Получен полный TCP-ответ ...`.

Результаты нельзя подменять подготовленными строками: наличие TC зависит от реального размера ответа, EDNS0 и настроек DNS-сервера. По условию пользователя код на этапе подготовки не запускался и не тестировался, поэтому скриншоты отсутствуют.
