# RDTP: проектирование надёжной передачи файла поверх UDP

**Вариант:** Go-Back-N (GBN) · **Язык:** C++20 · **Транспорт:** UDP/IPv4 · **Версия протокола:** 1

## 1. Архитектура и формат данных

Система состоит из двух независимых процессов: `rdt_sender` читает входной файл и передаёт его блоками, `rdt_receiver` принимает блоки строго по порядку и записывает выходной файл. UDP используется только как транспорт дейтаграмм. Надёжность, нумерация, контроль целостности, подтверждения и повторные передачи реализованы на прикладном уровне. Соединение логически идентифицируется парой «адрес и порт отправителя» и случайным 32-битным `sessionId`.

Каждая дейтаграмма содержит **24-байтный заголовок** и полезную нагрузку не более **1024 байт**. Многобайтные целые числа кодируются в сетевом порядке байтов (big-endian).

| Смещение | Длина | Поле | Назначение |
|---|---:|---|---|
| 0 | 4 | `magic` | ASCII `RDTP` (`0x52445450`) |
| 4 | 1 | `version` | Версия, всегда `1` |
| 5 | 1 | `type` | `START=1`, `DATA=2`, `ACK=3`, `FIN=4`, `FIN_ACK=5` |
| 6 | 2 | `reserved` | Нули |
| 8 | 4 | `sessionId` | Идентификатор передачи |
| 12 | 4 | `sequence` | Номер DATA или подтверждённого блока |
| 16 | 2 | `payloadLength` | Размер полезной нагрузки |
| 18 | 2 | `reserved` | Нули |
| 20 | 4 | `checksum` | CRC32 заголовка и данных |
| 24 | 0…1024 | `payload` | Содержимое блока или размер файла |

**Типы пакетов.** `START(seq=0)` содержит восьмибайтный `uint64` — длину файла; `ACK(0)` подтверждает начало. `DATA(seq=1…N)` содержит очередной блок файла, `ACK(k)` кумулятивно подтверждает все блоки вплоть до `k`. `FIN(seq=N+1)` завершает передачу, `FIN_ACK(N+1)` подтверждает завершение. Для пустого файла `N=0`, DATA отсутствуют.

**Контроль целостности.** CRC32 (полином `0xEDB88320`) рассчитывается для всего пакета при нулевых байтах поля `checksum`. Получатель отбрасывает пакеты с неверными magic, версией, типом, длиной, зарезервированными полями или CRC32. Неправильный DATA не записывается в файл.

## 2. Конечные автоматы участников

### Отправитель (Sender)

| Состояние | Событие | Действие и переход |
|---|---|---|
| `INIT` | Запуск | Открыть файл, определить `N`, выбрать `sessionId`; отправить START → `WAIT_START` |
| `WAIT_START` | `ACK(0)` | Начать передачу → `TRANSFER` |
| `WAIT_START` | Тайм-аут | Повторить START, пока не исчерпан лимит |
| `TRANSFER` | Свободное место в окне | Отправлять новые DATA без остановки на ожидании каждого ACK |
| `TRANSFER` | `ACK(k)` для отправленного блока | Сдвинуть левую границу окна до `k+1` |
| `TRANSFER` | Тайм-аут | Повторно отправить все ещё неподтверждённые DATA |
| `TRANSFER` | Подтверждены все DATA | Отправить FIN → `WAIT_FIN` |
| `WAIT_FIN` | `FIN_ACK(N+1)` | Успешно завершить → `DONE` |
| `WAIT_FIN` | Тайм-аут | Повторить FIN, пока не исчерпан лимит |

В `TRANSFER` поддерживаются `base` — первый неподтверждённый DATA — и `nextSequence` — номер следующего нового DATA. Передавать можно, пока `nextSequence < base + windowSize` и `nextSequence <= N`. Один таймер отслеживает отсутствие продвижения окна. Неактуальные и повторные ACK не сдвигают окно. При исчерпании количества попыток программа завершается с кодом ошибки.

### Получатель (Receiver)

| Состояние | Событие | Действие и переход |
|---|---|---|
| `WAIT_START` | Корректный START | Создать выходной файл, запомнить peer/сессию, отправить ACK(0) → `RECEIVING` |
| `RECEIVING` | Повторный START | Повторить ACK(0), не перезаписывая файл |
| `RECEIVING` | DATA с `seq=expected` | Проверить длину, записать блок, увеличить `expected`, отправить ACK(`expected−1`) |
| `RECEIVING` | DATA вне порядка | Не записывать; отправить ACK последнего принятого блока |
| `RECEIVING` | FIN после всех DATA | Сбросить файл на диск, отправить FIN_ACK → `LINGER` |
| `LINGER` | Повторный FIN | Повторить FIN_ACK и продлить ожидание |
| `LINGER` | Истекло время ожидания | Закрыть сокет и файл → `DONE` |

Получатель не буферизует блоки вне порядка: это принципиальное свойство GBN. Чужие `sessionId` или UDP-адреса игнорируются. Число ожидаемых DATA определяется размером файла из START. После FIN получатель остаётся доступен ограниченное время, поскольку последний FIN_ACK тоже может потеряться.

## 3. Алгоритм, ненадёжный канал и проверка

**Окно и тайм-ауты.** По умолчанию размер окна — **32 блока**, тайм-аут — **250 мс**, лимит — **100 повторных попыток без продвижения**. У каждого DATA нет отдельного таймера: по истечении общего тайм-аута повторно отправляются пакеты от `base` до `nextSequence−1`. Так устраняется простой «один пакет — один ACK» и достигается конвейерная передача. Повторные чтения делаются из исходного файла по смещению `(sequence−1) × 1024`; весь файл в оперативной памяти не хранится.

**Ненадёжный канал.** Перед фактическим `sendto()` независимый симулятор может (а) отбросить исходящий пакет с вероятностью `--loss`, (б) задержать его на случайное число миллисекунд в интервале `[0, --delay-ms]`. Симулятор применяется и к DATA/START/FIN у отправителя, и к ACK/FIN_ACK у получателя; поэтому для потерь подтверждений флаги надо задавать обоим процессам. Отложенная отправка выполняется неблокирующей очередью с периодическим обслуживанием через `poll()`. Ключ `--seed` позволяет воспроизвести сценарий.

**Статистика и наблюдаемость.** Отправитель показывает прогресс передачи и итоговые байты, время, скорость МиБ/с, долю симулированных потерь исходящих пакетов, число повторных передач, тайм-аутов и принятых ACK. Получатель выводит размер файла, скорость, потери исходящих ACK, число дубликатов/внеочередных DATA и ошибочных пакетов. С `-d` выводятся номера каждого DATA, ACK, FIN, симулированные потери, задержки и тайм-ауты. Проценты потерь вычисляются отдельно для исходящего потока каждого процесса, а не как единая оценка сетевого канала.

**Завершение и пределы.** Сессия начинается с подтверждённого START и заканчивается FIN/FIN_ACK. Для восстановления потерянного FIN_ACK получатель остаётся в `LINGER` 2500 мс по умолчанию и продлевает ожидание при повторном FIN. Количество DATA ограничено `2³²−2` блоками. Предполагается, что исходный файл не меняется во время отправки. Протокол не предоставляет шифрование, аутентификацию, управление перегрузкой TCP и одновременную обработку нескольких сессий — это вне задания.

**Проверка на Linux (локальный UDP).** Собрать `cmake -S . -B build && cmake --build build`; запустить получатель, затем отправитель. Сравнивать файлы побайтово или по SHA-256. Показательные сценарии: маленький текстовый файл (725 байт), большой бинарный (1 МиБ), пустой (0 байт), бинарный файл 24 КиБ с `--loss 0.20 --delay-ms 20 -d` у обоих процессов. Успешные и подробные логи находятся в `examples/logs/`. В проверенном сценарии потерь наблюдались повторные DATA, потерянные ACK и повторное подтверждение FIN; результирующий файл совпал с оригиналом.

**Соответствие ТЗ.** Применены POSIX `socket`, `bind`, `sendto`, `recvfrom`, `poll`, `close` через RAII-обёртку; обработка пакетов и файлов вынесена в отдельные модули; сборка — C++20. Решение реализует учебный RDTP поверх UDP, а не TCP из RFC 793.
